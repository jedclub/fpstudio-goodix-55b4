# FPStudio v0.3.3

Releases are now built with profile-guided optimisation.

## Changes

- Build the release with PGO. The workflow compiles once with counters, trains
  on the test suite - which drives the PAM conversation, the frame selector,
  the placement search and the matcher end to end, using no fingerprint data -
  and then compiles again against what was counted. Release build time roughly
  doubles.

## What it measured

Nothing, on this workload. Against the real 64-image gallery and held-out
captures of the enrolled finger, 36 searches per build with the order of every
trial randomised and the clock warmed first:

| build | median | 25% | 75% |
|---|---|---|---|
| `-O3` + LTO | 976.7 ms | 906.9 | 1445.3 |
| plus PGO | 972.0 ms | 921.8 | 1452.4 |

0.5%, Mann-Whitney p = 0.48. The expensive search is dispatched to the Vulkan
worker, so the CPU-side hot path is small and there is little for a profile to
rearrange.

Two earlier readings of this comparison were wrong in opposite directions, both
from letting the order of the runs carry the result: 33% faster when each build
was timed in one block, 14% slower when they were alternated in a fixed order
from a cold clock. Only the randomised, warmed measurement above is meaningful.

It is kept on because it costs build time rather than correctness - the suite
passes 26 of 26 twice over, and the matcher returns bit-identical scores - and
because the balance changes as soon as work moves back to the CPU, which is
what the fallback path on a machine without a usable Vulkan device is.

## Upgrade notes

- Nothing to re-enrol, and no driver change. `--refresh-experimental-auth`
  deploys the rebuilt matcher binaries and leaves the gallery, enrolment and
  PAM stacks alone.
- Do not read the table above as a reason to expect the lock screen to be
  faster. What fixed the lock screen was v0.3.2's driver change; this is a
  build setting.
