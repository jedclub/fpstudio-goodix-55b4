# fprintd 폭주 루프: 원인과 수정

## 무슨 일이 있었나

2026-09-17, 이 ThinkPad에서 `fprintd`가 **1시간 42분 동안 CPU 한 코어의 95.9%를
점유한 채 끝나지 않았다.** 수동 재시작 전까지 지문 센서는 아무 응답도 하지
않았다.

관측된 사실만 적는다.

| 항목 | 값 |
| --- | --- |
| 프로세스 | `/usr/lib/fprintd` (PID 338565) |
| 경과 / CPU 시간 | 1:42:28 / 1:38:19 (= 95.9%) |
| 로그 출력 | 초당 약 125,000줄 |
| journald 억제량 | 30초당 약 370만 건 |
| USB 장치 | 버스에 **정상 존재** (`27c6:55b4`, Bus 001 Device 004) |
| D-Bus | **정상 응답** (`GetDevices` → `Device/0`) |
| 반복 메시지 | `Receive data error: USB error on device 27c6:55b4 : No such device (it may have been disconnected) [-4]` |

스핀 중인 메인 스레드의 스택:

```
#0  transfer_finish_cb (../libfprint/fpi-usb-transfer.c:354)
#1  ?? (libgio-2.0)
#2  ?? (libglib-2.0)
#3  g_main_context_iteration
    ... 중첩 반복
```

## 원인

`libfprint/drivers/goodixtls/goodix.c`의 수신 콜백이 실패한 전송을 **조건 없이,
지연 없이, 횟수 제한 없이** 다시 제출한다.

```c
if (error)
  {
    fp_warn ("Receive data error: %s", error->message);
    g_error_free (error);
    goodix_receive_data (dev);   /* 즉시 재시도 */
    return;
  }
```

오류가 일시적일 때는 맞는 동작이다. 센서가 버스에서 떨어졌다가 **새 주소로 다시
열거되면** 데몬이 쥐고 있던 핸들은 죽은 핸들이 되고, 모든 재제출이 즉시
`LIBUSB_ERROR_NO_DEVICE`로 실패하며, 콜백이 중첩된 메인 컨텍스트 반복을 통해
자기 자신으로 재진입한다. 스택도 함께 자란다.

이 상태는 **스스로 풀리지 않는다.** fprintd의 30초 유휴 종료는 루프가 유휴
상태로 돌아가지 않으므로 영원히 발동하지 않는다.

### 부수 피해: 관측성 자체가 파괴된다

로그 폭주가 링 버퍼를 밀어내, 부팅(9/15 22:46) 이후 **약 이틀치 journal이
사라졌다.** 남은 기록은 폭주 시작 10분 전부터였다. 즉
[22-auth-observability](22-auth-observability.md)가 기반하는 인증 기록과
`fpstudio-auth-report`가 읽을 근거가 함께 날아간다. 데몬은 복구 가능했지만
증거는 아니었다.

## 수정

### 1. 드라이버 — 근본 수정

`src/driver/patches/0020-goodix55x4-bounded-receive-retry.patch`

재시도에 세 가지 한계를 둔다.

- **치명적 오류는 재시도하지 않는다.** `NO_DEVICE`, `NOT_OPEN`,
  `PERMISSION_DENIED`, `CANCELLED`은 같은 핸들로 아무리 반복해도 성공할 수
  없다. 읽기 루프를 끝내고 대기 중인 명령에 실패를 전달해, SSM이 이유를 들고
  실패하도록 한다.
- **일시적 오류는 지연 후 재시도한다.** 20 ms 타이머를 거치므로, 즉시 실패하는
  전송이 바쁜 루프가 될 수 없다.
- **일시적 오류도 무한하지 않다.** 연속 25회 또는 5초를 넘기면 포기한다.

로그도 버스트당 한 줄로 제한한다. 함께, 취소 경로에서 `GError` 하나가 새던 기존
누수도 고쳤다.

> 이 패치는 드라이버를 다시 빌드해 설치해야 효력이 생긴다.

### 2. systemd — 로그 폭주 피해 억제

`61-fpstudio-guard.conf` (GPU 드롭인과 분리 — 매처를 롤백해도 남는다)

```ini
LogRateLimitIntervalSec=10s
LogRateLimitBurst=500
```

위 패치로 이 루프는 더 이상 발생하지 않는다. 이 드롭인은 그 수정을 두 번 하는
것이 아니라, **같은 모양의 다른 고장**이 생겼을 때 journal이 함께 날아가지
않도록 하는 것이다. 이번에 데몬은 재시작으로 복구됐지만 원인을 이해할 근거는
이미 사라진 뒤였다.

정상적인 전체 등록이 수십 줄인 것에 비하면 한참 위이고, 폭주 루프보다는 네
자릿수 아래다.

### 워치독을 두지 않기로 한 이유

한때 CPU 점유를 감시해 fprintd를 강제 재시작하는 상주 워치독을 만들었다가
걷어냈다. 판단 근거를 남겨 둔다.

- 이 고장은 예측하지 못한 외부 조건이 아니라 **잘못 짠 재시도 루프**였다.
  고칠 수 있는 버그를 감시로 덮는 것은 순서가 뒤바뀐 대응이다.
- 워치독은 **인증 데몬을 강제 종료하는 상주 프로세스**다. 임계치를 잘못 잡으면
  정상 인증을 끊고, 그 자체가 새로운 고장 지점이 된다.
- 패치가 들어가면 워치독이 발동할 상태 자체가 만들어지지 않는다.

같은 종류의 고장이 다시 관측되면 그때 다시 논의할 문제이지, 지금 상주시켜 둘
근거는 없다.

다만 조사 과정에서 얻은 두 가지 사실은 기록해 둔다. 나중에 비슷한 판단을 할 때
쓸모가 있다.

- **D-Bus 응답성은 건강 지표가 될 수 없다.** 이번 사고 내내 `GetDevices`는 정상
  응답했다. D-Bus ping으로 감시했다면 102분 내내 "이상 없음"이었을 것이다.
- **`systemctl restart`의 종료 코드 0은 재시작 성공을 뜻하지 않는다.** 일부러
  스핀시킨 유닛으로 확인한 결과, 0을 반환하고도 MainPID가 그대로였다. 시그널
  핸들러를 돌릴 여유가 없는 프로세스는 `TimeoutStopSec`(기본 90초)까지 살아남고
  그동안 systemd는 작업을 정상으로 보고한다. fprintd는 glib 메인 루프에서
  시그널을 처리하는데, 폭주한 읽기 루프가 포화시키는 것이 바로 그 메인 루프다 —
  재시작이 가장 필요한 프로세스가 재시작 요청을 가장 알아채지 못한다. 수동으로
  복구할 때도 PID가 실제로 바뀌었는지 확인해야 한다.

## 함께 손본 것들

같은 종류의 고장(답이 틀린 게 아니라 **답이 오지 않고 기다림이 끝나지 않는**)을
전수 조사해 아래를 고쳤다.

| 위치 | 문제 | 대응 |
| --- | --- | --- |
| `pam_fpstudio.c` | `poll(..., -1)`에 상한 없음 | 센서에만 데드라인(비밀번호 입력은 무제한 유지) |
| `privrunner.cpp` | QProcess 타임아웃 전무 | 호출별 데드라인, terminate 후 kill |
| `setupwizard.cpp` | 등록·캡처·수정 작업에 감시 없음 | `guardOperation()` (등록 5분, 캡처 1분, 빌드 30분) |
| `auth_log_report.py` | journalctl 무제한 | 120초 타임아웃 + 50만 레코드 상한 |

`pam_fpstudio.c`의 데드라인이 **센서에만** 걸린다는 점이 중요하다. 전체 루프에
상한을 두었다면 멈춘 센서가 비밀번호 입력 취소로 바뀌었을 것이다. 비밀번호를
입력하는 사람은 원하는 만큼 시간을 쓸 자격이 있다.
