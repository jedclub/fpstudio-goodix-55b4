# 매처 최적화

측정으로 시작해서 측정으로 끝낸 기록이다. 세 번의 변경 모두 **결과를 바꾸지
않는 것**이 전제였다.

## 측정 환경

| 항목 | 값 |
| --- | --- |
| L1d | 32 KB, 8-way, 64 B 라인 |
| L2 / L3 | 512 KB / 4 MB |
| SIMD | AVX2 + FMA + BMI2 (AVX-512 없음) |
| 빌드 | `-O3` + LTO (프로젝트 기본 Release) |
| 프레임 | 108×88 = 9,504 픽셀 |

벤치마크는 합성 프레임이되 실물과 같은 모양(타원형 접촉 영역 안의 곡선 융선)을
쓴다. 이 코드의 제어 흐름이 데이터에 의존하기 때문이다 — 연결 요소, 세선화 반복
횟수, 특징점 개수가 모두 입력에 따라 달라지므로 평탄하거나 무작위인 영상은
아무도 실행하지 않는 경로를 재는 셈이 된다.

## 결과

프레임당(중앙값, 3회):

| 함수 | 전 | 후 | 배수 |
| --- | ---: | ---: | ---: |
| `extractMinutiae` | 9,255 µs | 1,762 µs | **5.25×** |
| `extractRidgeRegion` | 1,969 µs | 1,179 µs | **1.67×** |
| `assessInterior` | 3,984 µs | 2,523 µs | **1.58×** |
| 합계 | 15,207 µs | 5,464 µs | **2.78×** |

`assessInterior`는 직접 손대지 않았다. 내부에서 `extractRidgeRegion`을 두 번
부르기 때문에 같이 빨라졌다.

PMU (동일 작업량):

| 지표 | 전 | 후 | 변화 |
| --- | ---: | ---: | ---: |
| cycles | 16.99 B | 5.83 B | −65.7% |
| instructions | 58.33 B | 15.69 B | −73.1% |
| L1-dcache loads | 9.70 B | 4.52 B | −53.4% |
| L1-dcache misses | 38.0 M | 45.5 M | +19.8% |
| branches | 8.30 B | 2.90 B | −65.1% |
| branch-misses | 44.1 M | 25.3 M | −42.6% |
| 경과 | 4.65 s | 1.66 s | **2.80×** |

## L1 적중률은 목표가 아니었다

작업 시작 시 기준선 PMU는 이랬다.

- IPC **2.87**
- L1 적중률 **99.71%** (미스율 0.29%)
- 프레임당 12.5 M 명령어 = **픽셀당 1,318개**

즉 **캐시는 이미 거의 완벽했고 병목이 아니었다.** 9,504 픽셀 × 4 B = 38 KB가
L1에 거의 들어맞았고, 문제는 같은 데이터를 반복해서 읽는 **명령어 수**였다.

최적화 후 L1 미스는 오히려 19.8% **늘었고** 미스율은 0.41% → 1.01%로 나빠졌다.
그런데도 2.80배 빨라졌다. 총 적재량이 절반으로 줄었고(9.70 B → 4.52 B), 줄인
명령어 42.6 B가 늘어난 미스 7.5 M보다 압도적으로 비싸기 때문이다.

**최적화 대상은 적중률이 아니라 cycles였다.** 적중률만 보고 움직였다면 방향을
잘못 잡았을 것이다.

다만 L1을 무시해도 된다는 뜻은 아니다. 첫 시도에서 전체 프레임 크기의 보조
테이블(152 KB)을 잡았더니 L1 미스가 12.5 M → 44.0 M으로 **251% 폭증**했다.
아래 링 버퍼로 21 KB까지 줄여 18.1 M(−59%)으로 되돌렸고, 속도도 소폭 더
좋아졌다.

## 변경 내역

### 1. 지역 임계화 — 분리형 슬라이딩 윈도우 + 링 버퍼

`minutiae.h`. 프로파일이 지목한 지배적 비용이다.

11×11 창의 합과 제곱합을 픽셀마다 다시 읽고 있었다. 한 프레임에 9,504 × 121 =
**1,149,984회**의 곱셈-덧셈.

직사각형 창의 합은 **분리된다.** 가로 방향 이동 합 → 세로 방향 이동 합으로
바꾸면 출력 픽셀당 읽기가 121회에서 2회가 된다. 경계에서 창이 잘리는 것도
그대로 재현되며(나누는 개수는 실제로 합산한 사각형의 크기), 같은 사각형을
합하므로 결과는 부동소수점 결합 순서만 다르다.

세로 창 안에 있는 **11행만** 링 버퍼로 유지한다(19 KB). 여기에 열 누계(0.9 KB)를
더해 작업 집합이 약 21 KB로 L1 안에 들어가고, 열을 stride `w`로 훑는 대신
행 테이블을 순차 접근한다.

> 함정 하나: 창에 들어오는 행과 나가는 행은 정확히 `window`만큼 떨어져 있어
> **같은 링 슬롯을 공유한다.** 나가는 행을 먼저 빼고 나서 들어오는 행을 덮어써야
> 한다.

누산기는 `double`로 유지했다. `sd`가 거의 같은 두 값의 차이라 소거가 일어날 수
있고, 그 값을 고정된 0.022와 비교하기 때문이다.

### 2. 일관성 계산 — 초월함수 제거

`minutiae.h`. 이웃 픽셀마다 각도로 변환했다가 되돌리고 있었다.

```
theta = atan2(gy, gx) + pi/2
re   += e * cos(2*theta)
imag += e * sin(2*theta)        e = gx^2 + gy^2
```

후보 하나당 최대 81개 이웃 × 초월함수 3회. 그런데 **각도를 두 배 하는 것이
바로 표준 항등식이 되돌리는 연산이다.**

```
cos(2*theta) = -cos(2*phi) = -(gx^2 - gy^2) / e
sin(2*theta) = -sin(2*phi) = -(2*gx*gy)     / e
```

양쪽 모두 `e`가 곱해지고 있으므로 약분되어 다항식만 남는다.

```c
re     += gy*gy - gx*gx;
imag   -= 2*gx*gy;
energy += gx*gx + gy*gy;
```

이것은 근사가 아니라 **대수적 항등식**이다. 같은 양을 더 짧은 경로로 구한다.
초월함수는 후보당 2회(방향 보고용 `atan2`, `hypot` 내부)만 남는다.

프로파일상 `coherence`는 호출당 0.26 µs, 전체의 0.4%로 사실상 사라졌다.

### 3. Zhang-Suen 세선화 — 8이웃 비트 패킹 + 결정 테이블

`minutiae.h`. 프로파일에서 17.3%를 차지하던 구간.

판정에 필요한 모든 것(이웃 수, 링을 따라가는 0→1 전이 수, 단계별 삼중 조건)이
**여덟 이웃 중 어떤 것이 켜져 있는지에만 의존한다.** 경우의 수는 256가지이므로
8비트 정수의 성질이고, 조회로 답할 수 있다.

기존에는 전경 픽셀마다 인덱스 계산 8회, 스택에 8원소 배열 생성, 감싸기 연산이
있는 8회 루프를 최대 96패스 × 2단계 반복했다. 지금은 이웃을 링 순서 그대로
1바이트에 채우고(전이가 인접 비트가 되도록) 테이블 한 번을 읽는다. 세 행
포인터를 쓰므로 접근도 연속적이다.

`bits[]`가 엄밀히 0 또는 1이라 마스킹도 필요 없다.

211 µs → 110 µs (**1.91×**).

## 동등성 검증

속도보다 이쪽에 시간을 더 썼다.

400 프레임에 대해 원본과 최적화본의 출력을 덤프해 비교했다.

- **`extractRidgeRegion`**: 접촉 픽셀 수, 4×4 마스크, 커버리지, 중심 좌표,
  그리고 **이진 마스크 전체의 FNV 해시까지 바이트 단위로 동일**. 정수 덧셈은
  정확하고 결합법칙이 성립하므로 당연한 결과다.
- **`thinRidges`**: 같은 불리언 논리이므로 마찬가지로 완전 동일.
- **`extractMinutiae`**: 특징점 **개수·위치·종류·품질·usable 판정이 전부
  동일**. 유일한 차이는 `direction` 값이 소수점 6째 자리에서 갈리는 172건이다.

그 1e-6 rad 차이의 의미:

- 매칭 허용오차는 **35도 = 0.611 rad** (`assessMinutiae`) — **60만 배** 크다
- `direction`은 `float`이고 1.0 근처의 표현 정밀도가 약 6e-8 — 몇 ULP 수준

즉 대수적 재배치에 따르는 불가피한 반올림이며, 판정에 도달할 수 없는 크기다.

이와 별개로:

- 프로젝트 테스트 20/20 통과, 빌드 경고 0
- AddressSanitizer + UndefinedBehaviorSanitizer: 릭·경계 초과·UB 없음
  (검출기가 실제로 동작하는지는 의도적 릭으로 따로 확인했다 — LeakSanitizer는
  도달 가능한 메모리를 릭으로 보고하지 않으므로, 지역 포인터가 소멸하는 형태로
  대조군을 만들어야 한다)

## 프로파일 스코프

`tools/vkmatch/profile.h`. 다음 사람이 같은 질문을 하려고 계측을 다시 만들지
않도록 스코프를 소스에 남겼다.

**기본은 꺼져 있고, 꺼지면 아무것도 남지 않는다.** `FPSTUDIO_PROFILE`이 정의되지
않으면 매크로가 통째로 사라진다 — 분기도, 카운터도, 원자 연산도 없다. 측정하는
대상을 바꾸는 프로파일러는 의미가 없기 때문이다.

```sh
cmake -S src/fpstudio -B build -DFPSTUDIO_PROFILE=ON
```

검증: OFF 빌드의 프로파일 심볼 0개, ON 빌드 21개, 속도 차이는 잡음 범위.

스레드별 카운터는 소멸자가 없는 POD 배열이다. 처음에는 `thread_local
std::vector`였는데 **빈 표가 출력됐다.** 정적 리포터가 돌 때 벡터는 이미 파괴된
뒤였고, 파괴된 `std::vector`를 읽는 것은 UB라 `.empty()`는 거짓을 반환하면서
순회는 아무것도 내놓지 않았다. 집계 저장소도 같은 이유로 의도적으로 해제하지
않는다(정적 소멸 순서 문제의 표준 해법이며, 도달 가능하므로 릭 검사에도 잡히지
않는다).

출력 예:

```
scope                                   calls     total ms    us/call   share
ridge/extractRidgeRegion                 4422       611.92     138.38   35.7%
interior/assessInterior(pair)            1407       483.05     343.32   28.2%
minutiae/extractMinutiae                 1608       339.09     210.88   19.8%
minutiae/thinRidges                      1608       177.54     110.41   10.4%
minutiae/coherence                      26130         7.05       0.27    0.4%
```

(중첩 스코프이므로 비중은 겹친다.)

## 하지 않은 것과 그 이유

- **명시적 AVX2 인트린식**: 남은 핫 루프는 조기 탈출(`if(!mid[x])continue`)과
  테이블 조회가 섞인 형태라 자연스럽게 벡터화되지 않는다. 억지로 하려면 마스킹
  기반으로 재작성해야 하는데, 얻을 이득보다 검증 부담이 크다. 알고리즘 차원의
  변경(121회 → 2회)이 이미 SIMD로 얻을 수 있는 폭을 넘어섰다.
- **`float` 전환**: `sd` 계산의 소거 위험 때문에 `double`을 유지했다. 안정성을
  버리지 않는 것이 전제였다.
- **PGO / `-march=native`**: 배포 바이너리의 재현성과 이식성에 영향을 주므로
  별도 판단이 필요하다. `build-pgo*` 트리가 이미 있으니 필요할 때 그 경로로
  다루는 편이 맞다.

# GPU 경로 최적화

CPU 경로를 먼저 손댄 것은 순서가 틀렸다. 위 작업은 함수 안에서는 2.78배를
얻었지만 인증 전체에서는 약 2%였다. 실제 시간이 어디 있는지 먼저 쟀어야 했다.

## 어디에 쓰는가

실제 인증 기록(journal, 16건):

| 경로 | 건수 | 중앙값 |
| --- | ---: | ---: |
| 성공 (`refined=0`) | 4 | 1,082 ms |
| 실패 (`refined=1`, 광각 회전 탐색) | 12 | 2,552 ms |

레퍼런스 44장으로 실제 경로와 같은 호출을 합성해 재현한 뒤 분해했다.

| 구성 | ms | 비중 |
| --- | ---: | ---: |
| GPU 실연산 (`gpu_ms`) | 1,441 | 63% |
| CPU + 제출/동기화 | 853 | 37% |
| wall_ms | 2,294 | 100% |

CPU 시간은 벽시계의 31%뿐이었다. 즉 **GPU 대기가 지배적**이다.

## 측정이 먼저 무너졌다

같은 바이너리·같은 셰이더가 몇 분 간격으로 1,797 ms와 3,622 ms를 냈다. 온도는
43°C로 정상이었고, 원인은 `pp_dpm_sclk`이 **400 MHz**에 머물러 있는 것이었다 —
이 GPU의 전력 관리는 지속적인 부하를 받기 전까지 클럭을 올리지 않는다.

그래서 이후의 모든 수치는 **워밍업 4회 → 조건 교대 8~10라운드 → 최솟값**으로
잰다. 최솟값은 클럭이 가장 높았던 상태를 뜻하고, 이 방식에서는 중앙값과
최솟값이 3% 안으로 붙는다. 워밍업 없이 블록 단위로 재면 조건 간 차이가 클럭
변동에 묻힌다.

## 1. 셰이더 — probe 텍셀 로드 20 → 12

샘플 하나당 버퍼 로드가 25회였다(레퍼런스 5, probe 20). 어느 쪽이 비싼지
절제 실험으로 확인했다. probe 그래디언트의 bilinear 4회만 제거하자 동일 가설
수에서 **`gpu_ms`가 55.4% 감소** — 이 셰이더는 샘플/메모리 바운드다.

probe는 샘플마다 다섯 번 읽힌다: 중심 `q`, 그리고 그래디언트가 필요로 하는
`q±(1,0)`, `q±(0,1)`. 다섯 번을 각각 `sampleImage()`로 부르면 20회지만, 오프셋이
**정수 픽셀**이므로 다섯 footprint가 모두 `floor(q)`의 4×4 이웃 안에 들어가고
소수부도 전부 같다. 실제로 쓰이는 텍셀은 12개다.

```
   . X X .      X = 어떤 샘플이든 읽는 텍셀
   X X X X      . = 4x4 안이지만 아무도 안 읽음
   X X X X
   . X X .
```

12개를 한 번 가져와 다섯 보간을 그 위에서 만든다. `mix()` 연산과 피연산자가
그대로이므로 결과는 동등이 아니라 **동일**하다. 경계 클램프도 원래
`sampleImage()`가 적용하던 위치 그대로 유지했다 — 진입 조건이 `q`를
`[1,width-2]×[1,height-2]`로 묶으므로 `c-1`은 항상 유효하고 `c+1`은 클램프가
필요 없으며, 바깥 열·행(즉 `+x`, `+y` 이웃의 것)만 클램프 대상이다.

## 2. 제출 청크 2048 → 65536

`Chunk`는 하드웨어 한계가 아니었다 — 이 장치의
`maxComputeWorkGroupCount[0]`은 4,294,967,295다. 2048은 인증 1회(가설
515,032개)에 **252번의 제출-대기 왕복**을 뜻했고, 루프가 완전히 직렬이라
(pack → submit → `vkWaitForFences` → copy) CPU와 GPU가 전혀 겹치지 않는다.

최적화 셰이더 기준 재스윕(8라운드 교대, 최솟값):

| chunk | 제출 | wall_ms | 비-GPU |
| ---: | ---: | ---: | ---: |
| 512 | 987 | 2,151 | 1,049 |
| 2,048 | 247 | 2,056 | 933 |
| 16,384 | 31 | 1,966 | 748 |
| 65,536 | 8 | 1,807 | 754 |

중간에 "작은 청크가 L2 지역성이 좋아 더 빠르다"는 역전이 한 번 보였는데,
워밍업을 제대로 넣으니 사라졌다. 노이즈였다.

## 결과

2×2 교차 측정(워밍업 후 10라운드 교대, 최솟값):
