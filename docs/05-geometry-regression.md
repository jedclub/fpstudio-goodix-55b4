# `0/72` 의 원인 — 행 길이를 잘못 바꾼 것이었다

등록은 10/10 통과하는데 검증이 어느 등록본에 대해서도 `0/72`로 나왔다.
임계값은 150이다. 원인은 이 저장소가 직접 만든 패치 `0006`이었다.

## 무엇을 잘못했나

패치 `0006`은 센서 기하를 `108 x 88`에서 `88 x 108`로 바꿨다. 근거는 둘이었다.

- `goodix-fp-dump`의 `driver_55x4.py`가 `SENSOR_WIDTH = 88`, `SENSOR_HEIGHT = 108`
- 벤더의 `Wbdi.dll`이 들고 있는 센서별 파라미터 표에 이 부품 행이 `(800, 88, 108)`

둘 다 맞는 값이다. **다이의 물리적 기하**를 말한다는 점만 빼면.

센서는 자기 물리 기하가 아니라 **명령받은 스캔 창**대로 픽셀을 내보낸다.
드라이버가 `ACTIVATE_SET_MCU_CONFIG`에서 올리는 256바이트 MCU config가 그
스캔 창을 정하는데, 그 블롭은 GF3268의 것이다 — `Wbdi.dll` 오프셋 1567568의
상수와 256바이트 중 251바이트가 같고, 첫 차이는 바이트 192의 `0x14` vs `0x15`다.

그러니 GF3208 다이에 GF3268 블롭을 올린 이 드라이버에서 나오는 행 길이는
108이다. 상류 값이 처음부터 맞았다.

## 어떻게 확인했나

행 길이가 틀리면 이미지가 매 행마다 조금씩 밀린다. 그래서 세로로 인접한
픽셀이 서로 안 닮게 된다. 9504픽셀 원본에 대해 후보 행 길이별로 세로 인접
픽셀의 평균 절대차를 계산했다. 참값에서 최소가 된다.

```
108 x  88   309.5     <- 드라이버 원래 값
216 x  44   400.0
 88 x 108   411.6     <- 패치 0006이 넣은 값
 96 x  99   417.0
 44 x 216   424.5
```

되돌린 뒤 실제로 캡처한 결과가 확증한다.

| | 행 편차 | 열 편차 |
|---|---|---|
| `88 x 108` (패치 적용) | 115.8 | 10.2 |
| `108 x 88` (되돌림) | 29.7 | 35.0 |

행 편차가 열 편차보다 11배 크던 것이 거의 같아졌다. 방향 편향이 사라졌다는
뜻이고, 눈으로 봐도 대각선 능선이 선명한 정상 지문이 나온다.

## 이 과정에서 잘못 짚은 것

되돌리기 전 덤프만 보고 "프레임에 지문이 아예 없다"고 판단한 적이 있다.
근거는 이랬다.

- 손가락 프레임과 배경 프레임의 상관계수 `+0.9585`
- 두 프레임 차이가 전 픽셀에서 균일 (하위25% 594 / 중앙 724 / 상위25% 848)
- 행별 DC를 제거한 뒤 가로 자기상관이 lag 8~12에서 부활하지 않음 (-0.09)

전부 잘못된 기하 위에서 잰 값이다. 세 번째는 특히 함정이었다 — 이 손가락의
능선은 대각선으로 흐르므로 **가로 방향** lag 8~12에서는 능선 주기가 잡히지
않는다. 기하가 깨져 있을 때는 그 위에서 잰 어떤 통계도 원인 추정에 쓸 수 없다.

## 기하를 고친 뒤에도 남은 것 — 정규화가 대비의 절반을 버린다

기하를 되돌리자 이미지는 정상이 됐지만 검증은 여전히 `0/72`였다. 매처를
그대로 복제해 실측했다.

| 비교 | descriptor 매칭 | 길이일관 쌍 | 점수 |
|---|---|---|---|
| 같은 이미지끼리 | 149 | 6216 | 14,601,260 |
| 서로 다른 두 캡처 | 12 | 5 | 0 |

파이프라인은 정상이다. 점수 구조를 보면 `sigfm_match_score`는 두 번 조기
탈출한다 — descriptor 매칭이 5개 미만일 때, 그리고 길이가 5% 이내로 일치하는
쌍이 5개 미만일 때. 72점을 넘으려면 길이일관 쌍이 13개 이상 필요하고,
그러려면 매칭이 30개 안팎은 나와야 한다.

출력 히스토그램이 이유를 알려줬다. 5장 모두 명목상 0~255를 다 쓰지만
**1번째 백분위가 전부 0**이고 중앙값은 122~189였다. 접촉하지 않은 어두운
영역이 min/max 정규화의 흑점을 잡아버려서, 실제 능선은 위쪽 절반에 눌려 있다.
SIFT의 DoG 검출기는 국소 대비가 낮은 극점을 버리므로 이게 그대로 키포인트
손실이 된다.

접촉 영역만 남기고 2~98 백분위로 다시 늘려 같은 두 장을 재채점했다.

```
원본 min/max      매칭 10  길이일관  7   점수  5
백분위 정규화     매칭 14  길이일관 18   점수 63     <- 임계값 72
+CLAHE            매칭 12  길이일관 12   점수 24
```

이미지도 매처도 그대로고 정규화만 바꿨는데 5점이 63점이 됐다. CLAHE를 더
얹으면 오히려 나빠진다 — 국소 대비 평활화가 SIFT가 쓰는 전역 구조를 깨뜨린다.

패치 `0009`가 `squash_frame_linear`를 이 방식으로 바꾼다. 어두운 하위
15%를 접촉하지 않은 영역으로 보고 제외한 뒤, 남은 구간의 2~98 백분위를
늘린다. 양 끝을 자르는 것은 의도적이다 — 잘리는 쪽은 죽은 영역과 포화된
능선 꼭대기라 어느 쪽도 정보를 담고 있지 않다.

한 가지 남는다. 서로 다른 부위를 찍은 쌍(s3-s4, s4-s5)은 백분위 정규화
후에도 0이다. 센서가 5.5 x 4.5mm로 작아 배치가 조금만 달라도 겹침이
급감하기 때문이고, 이것이 등록본 10장이 존재하는 이유다.

## OTP — 별개의 미비점

원인을 찾는 중에 확인한 것이라 여기 남긴다. 이 드라이버는 칩별 보정을 전혀
읽지 않는다. `activate_run_state()`에 호출부가 주석으로만 있고

```c
// case ACTIVATE_SET_ODP:
//     goodix_send_read_otp(dev, read_otp_callback, ssm);
//     break;
```

`read_otp_callback`은 작성된 적이 없다. 구조체의 `guint8 *otp;`도 미사용이다.
전송 계층은 멀쩡하다 — `GOODIX_CMD_READ_OTP (0xa6)`, `goodix_send_read_otp()`.

`Wbdi.dll`의 문자열이 OTP 내용을 알려준다.

실제로 읽어낸 값은 32바이트였다.

```
0827876a 54ace1ed a88e560a 020452e6 c20c9864 0335d728 05000000 c0165032
```

```
milan_hu_series_update_dac_register_from_otp
[otp info]tcode: 0x%x, diff: 0x%x, touch_diff: 0x%x,  fdt_tcode: 0x%x
[otp info]DACH: 0x%x : 0x%x : 0x%x : 0x%x
[otp info]DACL: 0x%x : 0x%x : 0x%x : 0x%x
_MilanFSerGetFdtOffsetFromOtp / GetDacFromOtp / GetTcodeAndDiffFromOtp
```

DAC는 판독 바이어스를, tcode는 적분 시간을 정한다. 다이마다 다른 값인데
우리는 GF3268용 고정 블롭 하나만 올린다. 지금 이미지가 쓸 만하게 나오므로
**이것이 `0/72`의 직접 원인은 아니었다.** 다만 위에서 본 대로 대비가 매칭
개수를 그대로 좌우하므로, 아날로그 동작점을 제대로 잡는 것은 여전히 남은
개선 여지다.

패치 `0008`이 `ACTIVATE_READ_OTP` 상태를 추가해 OTP를 읽고 로그에 그대로
찍는다. 읽기 전용이고 실패해도 치명적이지 않다. 레이아웃은 추측하지 않고
실제 바이트를 보고 정한다.

## 교훈

데이터시트와 참조 구현이 말하는 값이 맞더라도, **그 값이 우리 코드 경로에서
의미하는 바가 같은지**는 따로 확인해야 한다. 여기서는 "센서의 기하"와
"센서가 지금 내보내는 기하"가 다른 것이었고, 그 차이를 만드는 것이 우리가
직접 올리는 config 블롭이었다.

## 실측 결과

정규화까지 고친 뒤 재등록하고 7회 검증했다. 임계값은 72다.

| 회차 | 최고 점수 | 결과 |
|---|---|---|
| 1 | 137 | 일치 |
| 2 | 0 | 실패 |
| 3 | 7 | 실패 |
| 4 | 928 | 일치 |
| 5 | 669 | 일치 |
| 6 | 77 | 일치 |
| 7 | 2920 | 일치 |

7회 중 5회 성공. 눈여겨볼 것은 분포다. 성공할 때는 임계값을 압도적으로
넘기고(669, 928, 2920) 실패할 때는 0이나 7이다. 중간이 거의 없다.

점수가 매칭쌍들의 쌍에 대한 이중 루프 개수이므로 겹침이 조금만 확보되면
값이 제곱으로 튀고, 못 미치면 `angles.size() < 5` 게이트에서 그대로 0이
되기 때문이다. 즉 실패는 품질 문제가 아니라 **배치 문제**다 — 5.5 x 4.5mm
창에 등록본 10장 어디와도 겹치지 않는 위치로 올라온 경우다.

남은 개선 여지는 이미지 대비다. 위에서 본 대로 대비가 매칭 개수를 그대로
좌우하고, 매칭 개수가 점수를 제곱으로 좌우한다. 칩별 OTP 보정(DAC/tcode)을
config 블롭에 반영하는 것이 그 방향이고, 패치 `0008`이 그 첫 단계로 실제
OTP 바이트를 읽어 남긴다.

## 등록 품질 게이트

7회 중 2회 실패의 성격은 분명했다. 실패는 0점과 7점이고 성공은 77~2920점이다.
중간이 없다. 즉 화질이 아슬아슬해서 진 것이 아니라 **겹칠 곳이 없어서** 진 것이다.

그렇다면 등록본의 질이 곧 성공률이다. 그런데 지금 등록은 캡처된 것을
무조건 받는다. 손가락이 67%만 닿은 프레임도 한 칸을 차지하고, 그 칸은
나중 어떤 시도와도 겹치지 못하므로 영원히 기여하지 않는다. 108x88 —
약 5.5 x 4.5mm — 창에서 그런 칸은 낭비 이상이다.

실제 캡처 5장으로 두 지표를 재봤다.

|  | 접촉률 | 선명도 | |
|---|---|---|---|
| s1 | 95.7% | 16.0 | 완전 접촉 |
| s3 | 93.4% | 15.8 | 완전 접촉 |
| s4 | 95.5% | 15.1 | 완전 접촉 |
| s2 | 67.1% | 11.8 | 부분 접촉 |
| s5 | 76.8% | 10.9 | 부분 접촉 |

접촉률은 죽은 문턱(24)을 넘는 픽셀의 비율이다. 백분위 정규화 후 닿지 않은
영역은 0에 붙으므로, 이 값은 곧 손가락이 센서를 얼마나 덮었는가다.
선명도는 평균 절대 라플라시안으로, 다른 질문에 답한다 — 닿은 부분에 능선
구조가 있는가, 아니면 뭉갠 자국인가.

두 지표가 같은 방향으로 갈리는 것은 우연이 아니다. 덜 닿은 손가락은 덜
누른 손가락이고, 그러면 능선도 약하게 돌아온다. 어느 하나만으로도 이 다섯
장은 정확히 갈린다. 둘 다 요구하는 것은 각자가 못 잡는 경우를 위해서다 —
꽉 눌린 뭉갬, 그리고 직전 접촉이 남긴 전면적인 잔상.

패치 `0011`이 기준을 85% / 13으로 두고, 미달이면
`fpi_image_device_retry_scan()`으로 되돌린다. 등록 단계는 소비되지 않는다.
사유를 `FP_DEVICE_RETRY_CENTER_FINGER`와 `FP_DEVICE_RETRY_GENERAL`로
구분해서 올리므로, fpstudio가 배너에 서로 다른 지시를 띄운다.

기준을 후하게 잡은 이유가 있다. 두 오류는 대칭이 아니다 — 잘못 거부하면
한 번 더 대면 되지만, 잘못 통과시키면 등록이 끝날 때까지 칸 하나를 잃는다.
그럼에도 다섯 장으로는 경계를 정밀하게 놓을 수 없고, 자주 걸리는 게이트는
15단계 등록을 고역으로 만든다. 그래서 통과 쪽으로 기울여 뒀다.

패치 `0010`은 등록 단계를 10에서 15로 올린다. 이것은 규칙이 아니라
드라이버 상수다 — libfprint의 이미지 장치 기본값은 오히려 5(`IMG_ENROLL_STAGES`)
이고, `fpi_device_set_nr_enroll_stages`는 `> 0`만 검사한다. 단계마다
`fpi_print_add_print`가 샘플을 하나씩 누적하고 검증이 그 전부를 순회하므로,
단계 수는 곧 템플릿이 덮는 면적이다. 다만 순서가 있다 — 칸을 늘리기 전에
낭비되는 칸을 먼저 막아야 한다.

## 선명도가 성공을 예측한다

15단계 등록 후 검증을 재보니 이 관계가 나왔다.

| 회차 | 선명도 | 점수 | |
|---|---|---|---|
| 3 | 21 | 23 | 실패 |
| 4 | 28 | 1349 | 일치 |
| 5 | 30 | 1686 | 일치 |

드라이버의 게이트 문턱은 16이지만 실제 경계는 그보다 위다. 21은 통과해
놓고 졌고, 28~30은 임계값 72를 20배 넘겨 이겼다. 즉 게이트가 받아준
프레임 중에도 이길 것과 질 것이 갈린다.

그래서 수치를 화면에 띄운다. 손가락이 아직 센서에 있는 동안에만 사람이
손쓸 수 있는 정보이기 때문이다. fpstudio가 이미지 아래에 두 개의 막대로
보여주고, 선명도가 24 미만이면 통과했더라도 "흐립니다"를 함께 띄운다.

전달 경로에 한 가지 함정이 있었다. 드라이버의 다른 출력들은 `g_print`를
쓰는데, 이것은 GLib 로그 라이터를 거치지 않으므로 fpstudio가 볼 수 없다.
품질 줄만 `g_message`로 낸다. 이 차이를 모르고 넣었던 첫 버전은 배너에
"다시 대주세요" 안내가 영영 뜨지 않는 상태였다.

막대의 범위도 임의가 아니다. 접촉은 0~83인데, 백분위 정규화가 어두운
1/6을 0으로 잘라내므로 **구조적으로 83%가 상한**이기 때문이다. 100으로
잡으면 잘 댄 스캔도 3/4만 찬 것처럼 보인다.
